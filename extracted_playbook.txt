reaches the same conclusions, and charges you the same tokens for
the privilege. The model got 10x smarter in two years. It still forgets
everything after every session. This note presents the 5-layer

 I. THE PROBLEM: AMNESIA AT SCALE
 Why the smartest model in the world forgets everything
Every model call starts with an empty context
window. The previous session's discoveries,
decisions, corrections, and preferences are gone.
The agent that spent 40 minutes debugging a
migration script yesterday does not remember the
script exists today. It will read the same files, try the
same approaches, hit the same dead ends, and bill
you the same tokens [1].
 The industry invested heavily in making models
smarter — larger context windows, better
reasoning, faster inference. But intelligence without
memory is Groundhog Day. A brilliant colleague
who forgets every conversation is not a colleague.
They are an expensive consultant you must re-brief
every morning.
 The CoALA framework (Cognitive Architectures
for Language Agents) provides the vocabulary:
working memory, episodic memory, semantic
memory, procedural memory [2]. These are not
metaphors borrowed from psychology. They are

 II. LAYER 1: WORKING MEMORY
 The context window — everything the agent sees right now
Working memory is the context window. It contains
the system prompt, the current conversation, tool
results, retrieved documents, and any injected state.
When the context fills up, old content is either
truncated or compressed. This is where most agents
stop — and it is exactly why they forget [2].

B. The Overflow Problem
When the context window fills, the agent must
choose what to keep and what to discard. Most
systems truncate from the beginning — removing
the oldest messages first. This destroys the task
definition, early decisions, and the reasoning that
led to the current state. The better approach:
overflow important content into episodic memory
before it is lost.
Listing 1 — Context Overflow Handler
def handle_overflow(context, episodic_store, budget):
  if len(context.tokens) > budget * 0.85:
    # Save important content before truncation
    decisions = extract_decisions(context)
    facts = extract_facts(context)
    episodic_store.save(decisions, facts)
    # Compact context, keep recent + saved refs
    context.compact(keep_recent=budget*0.6)
  return context
 III. LAYER 2: EPISODIC MEMORY
 What happened — interaction logs with timestamps and outcomes
Episodic memory records what happened during
agent interactions: which tasks were attempted,
what approaches were tried, which succeeded,
which failed, and why. It is the agent's experience
log. Without it, the agent repeats mistakes and
re-discovers solutions [2].
A. What to Store
Not everything belongs in episodic memory. Store:
task descriptions and outcomes, tool calls and their
results, errors and their resolutions, decisions and
their reasoning, user corrections and preferences.
Do not store: verbose reasoning chains (compress
them), raw document contents (reference by ID), or
intermediate drafts (keep only the final version and
the key revision points).

B. Retrieval Strategy
When a new task arrives, the agent should query
episodic memory for similar past tasks before
starting work. Similarity can be computed by task
description embedding, tool overlap, or explicit
tags. The retrieved episodes tell the agent: this task
is similar to task-042, which failed because the
migration script had a typo in line 47. Skip directly
to the fix. This single retrieval saves the entire
debugging session [3].
C. Expiration
Episodic memory without expiration grows
indefinitely. Old episodes become irrelevant — the
codebase changed, the API was updated, the user's
preferences evolved. Set a retention policy: keep
the last 90 days by default, archive episodes with
high-value outcomes permanently, expire routine
episodes after 30 days. Let the user override with
explicit pins.
 IV. LAYER 3: SEMANTIC MEMORY
 What is true — facts, entities, and relationships as a knowledge
 graph
Semantic memory stores durable facts about the
world: "user prefers TypeScript," "the API endpoint
is /v2/users," "the production database is on AWS
us-east-1." These facts do not expire when the
session ends. They are the agent's accumulated
knowledge — distilled from episodic experiences
into a queryable store [2].

B. The Ontology Layer
Snowflake's research showed that adding a single
ontology layer — a schema that defines entity
types, relation types, and validation rules —
improved agent accuracy by 20% and reduced tool
calls by 39% [4]. The ontology is not complex. It is
a simple definition: users have names and
preferences, projects have owners and deadlines,
APIs have endpoints and authentication methods.
The schema constrains what the agent stores and
how it queries, preventing the knowledge base from
becoming a dump of unstructured observations.

C. Conflict Resolution
When the agent learns that the user now prefers
Python over TypeScript, it must update the
semantic memory — not append a second
preference. Conflict resolution is the operation that
keeps semantic memory consistent: detect
duplicates, merge compatible facts, supersede
outdated ones, and flag genuine contradictions for
human review. Without conflict resolution,
semantic memory accumulates contradictions that

 V. LAYER 4: PROCEDURAL MEMORY
 How to do things — methods that worked, saved as reusable skills
Procedural memory stores methods. The agent tried
three approaches to deploy the frontend. One
worked. That approach becomes a reusable skill: a
named method with steps, tools, preconditions, and
success criteria. Next time the task appears, the
agent loads the skill and skips straight to what
worked [2].

B. Skill Promotion
Not every successful approach deserves to become
a skill. Promote a method only when: the task
recurs at least weekly, the method has succeeded at
least three times, the steps can be described without
ambiguity, and the tools required are reliably
available. A single lucky success is an episode, not
a skill. The bar for promotion prevents procedural
memory from filling with brittle, context-dependent
methods.
C. Skill Versioning
When the deployment process changes, the old skill
becomes invalid. Version skills like software:
update the steps, increment the version number,
keep the previous version available for rollback,
and re-validate against the current environment. A
stale skill is worse than no skill — it produces
confident wrong behavior.
 VI. LAYER 5: FORGETTING
 What to delete — the most important layer nobody builds
An agent that never forgets accumulates
contradictions. The user moved from New York to
London, but the agent still recommends restaurants
in Brooklyn. The API migrated from v1 to v2, but
the agent still calls v1 because both endpoints exist
in semantic memory. The deploy process changed,
but the agent still follows the old skill because it has
a higher success rate from historical runs [5].
A. Forgetting Is Not a Bug
In human cognition, forgetting is a feature. It
prevents irrelevant memories from overwhelming
relevant ones. It resolves contradictions by letting
outdated facts decay. It reduces cognitive load by
pruning information that no longer matters. Agent
memory systems need the same mechanism — a
deliberate forgetting engine that prunes, supersedes,
and resolves [5].

Mem0 (51K+ GitHub stars) implements a memory
layer that sits between the application and the LLM.
Instead of stuffing the entire conversation history
into every API call, Mem0 extracts and stores
relevant facts in a persistent store. When the next
query arrives, only the relevant facts are injected —
typically 1,800 tokens instead of 26,000. The result:
90% fewer tokens per query and 91% lower
latency. The memory layer paid for itself within the
first day of deployment for every production user
who reported metrics [3].
B. Snowflake: Ontology Beats Brute Force
Snowflake's AI engineering team tested agent
performance with and without an ontology layer on
their internal data platform. The ontology defined
entity types (tables, columns, users, queries),
relation types (owns, depends_on, queries), and
validation rules. With the ontology, agent accuracy
improved by 20% and tool calls decreased by 39%.
The ontology did not add information the agent did
not have. It organized existing information so the
agent could find and use it efficiently [4].
C. Anthropic: Scoped Memory Isolation
Anthropic's Claude implements memory with strict
project-scoped isolation. Facts stored in one
project's memory are invisible to other projects.
This prevents cross-contamination: a coding agent's
preferences do not leak into a writing agent's style.
The architecture treats memory as a first-class
security boundary, not just a convenience feature.
Each memory store has its own read/write
permissions, expiration policies, and audit trail [7].
D. The Frontier Agent Gap
Research on SWE-bench and similar benchmarks
shows that frontier models reach only 62.2% on real
long-horizon tasks requiring more than 20 tool
calls. The primary failure mode is not reasoning —
it is context loss. The agent forgets what it
discovered in step 3 by the time it reaches step 15.
Multi-step tasks require memory, and memory
requires architecture, not just a bigger context
window.

F. The Memory Tax
Memory is not free. Every retrieval adds latency.
Every stored fact consumes storage. Every
forgetting operation requires computation. The
architecture must justify itself: if the token savings
from memory retrieval exceed the cost of
maintaining the memory system, the architecture
pays for itself. Mem0's numbers (90% token
reduction) show this is achievable, but only with
disciplined storage — not by saving everything.

 VIII-B. IMPLEMENTATION PATTERNS
 Production code for each memory layer
A. Episodic Memory with JSONL
The simplest episodic store is a JSONL file — one
JSON object per line, appended after each task.
JSONL is append-only by nature, which means no
corruption from concurrent writes. Each line
contains the episode record from Listing 2. To
retrieve relevant episodes, read the last N entries or
filter by keyword in the task description.
Listing 6 — Episodic Store Implementation
class EpisodicStore:
  def __init__(self, path='memory/episodes.jsonl'):
    self.path = path
  
  def save(self, episode):
    with open(self.path, 'a') as f:
      f.write(json.dumps(asdict(episode))+'\n')
  
  def retrieve(self, query, top_k=5):
    episodes = [json.loads(l) for l in open(self.path)]
    scored = [(ep, similarity(query,
ep['task_description']))
              for ep in episodes]
    scored.sort(key=lambda x: x[1], reverse=True)
    return [ep for ep, _ in scored[:top_k]]
B. Semantic Memory with SQLite
For production semantic memory, SQLite provides
durability, querying power, and zero infrastructure.
The schema defines entity types, relation types, and
fact records. Each fact has a source (which episode
produced it), a timestamp, and a status (active,
superseded, or flagged). This is the minimum viable
knowledge graph.

 XI. LIMITATIONS
A. Memory Is Not Understanding
Storing facts does not guarantee the agent uses them
correctly. A semantic memory entry "user prefers
TypeScript" does not help if the agent cannot
translate that preference into code-generation
decisions. Memory augments the model's
reasoning; it does not replace it. The memory
architecture makes more information available. The
model must still reason about it.
B. Forgetting Can Lose Important Context
A too-aggressive expiration policy deletes episodes
that contain crucial one-time decisions. A
too-conservative policy accumulates noise. The
correct balance depends on the domain: a medical
agent should retain episodes for years; a coding
agent can expire most episodes after 30 days. Let
users pin important episodes that should never
expire.
C. Semantic Memory Requires Maintenance
Facts change. APIs move. Teams reorganize.
Preferences evolve. A semantic memory that was
accurate in January may be dangerously wrong in
September. Schedule regular audits: compare stored
facts against current reality. Flag facts that have not
been confirmed in 90 days. Let users correct facts
directly.

B. The Reader-Writer Problem
When two agents update the same semantic fact
simultaneously, one write overwrites the other. The
memory system needs a concurrency strategy:
last-write-wins (simple but lossy),
merge-on-conflict (complex but complete), or
single-writer-per-entity (simple and safe). For most
production systems, single-writer-per-entity is the
correct default: each fact is owned by one agent,
and other agents read but do not write.
C. Memory as the Shared Brain
In the SpaceXAI Playbook architecture, the
Manager Bot maintains a ledger of all tasks,
owners, states, and deadlines. This ledger IS the
shared semantic memory. Specialist bots read it to
understand what work is available and write their
results back. The ledger replaces
conversation-based coordination: agents do not
message each other. They read and write to a shared
store. The result is a system that scales without the
N-squared communication problem of direct
agent-to-agent messaging.

 XIII. ADVANCED MEMORY PATTERNS
 Techniques for production-scale memory systems
A. Hierarchical Summarization
When episodic memory grows beyond thousands of
entries, raw retrieval becomes noisy. Hierarchical
summarization compresses old episodes into
summaries at increasing time scales: daily
summaries from individual episodes, weekly
summaries from daily summaries, monthly
summaries from weekly summaries. The agent
queries the most recent detailed episodes plus the
compressed summaries of older periods. This
provides both recent precision and long-range
context without unlimited storage growth [3].
Listing 10 — Hierarchical Summarization
def summarize_hierarchy(episodes, llm):
  # Group by day
  by_day = group_by_date(episodes)
  daily_summaries = []
  for day, day_eps in by_day.items():
    if len(day_eps) > 5:
      summary = llm.summarize(day_eps)
      daily_summaries.append(DailySummary(
        date=day, summary=summary,
        episode_count=len(day_eps),
        key_outcomes=[e.outcome for e in day_eps]
      ))
      # Archive raw episodes
      for ep in day_eps:
        ep.status = 'archived'
  return daily_summaries
B. Memory-Aware Routing
In multi-agent systems, memory can drive task
routing. When a new task arrives, the router queries
episodic memory to find which agent has the most
experience with similar tasks. The agent with the
highest success rate on similar past tasks receives
the assignment. This is implicit specialization
through memory — agents develop expertise not
through explicit role assignment but through
accumulated experience [6].
Listing 11 — Memory-Aware Router
def route_by_memory(task, agents, memory):
  best_agent = None
  best_score = 0
  for agent in agents:
    past = memory.episodic.retrieve(
      query=task.description,
      agent_id=agent.id, top_k=5)
    success_rate = sum(
      1 for ep in past if ep.outcome == 'success'
    ) / max(len(past), 1)
    if success_rate > best_score:
      best_score = success_rate
      best_agent = agent
  return best_agent or agents[0] # default to first
C. Contradiction Detection Pipeline
Contradictions in semantic memory are silent
killers. The agent stores "deploy target: staging"
and later stores "deploy target: production" without
superseding the first entry. Both facts are active.
The agent may use either one depending on
retrieval order. A contradiction detection pipeline
runs periodically, compares all active facts for the
same entity-relation pair, and either auto-resolves
(keep newer) or flags for human review.

A. Coding Agents
Coding agents benefit most from procedural
memory. The deploy process, the test commands,
the linting rules, the code patterns that pass review
— these are methods that should be saved as skills
after three successful uses. Episodic memory
captures debugging sessions: what was tried, what
failed, what fixed it. Semantic memory stores
project facts: which framework, which version,
which patterns are banned. The forgetting engine
expires episodes older than 90 days but preserves
skills indefinitely.
B. Customer Support Agents
Customer support agents need long-term semantic
memory. The customer's name, account type,
previous issues, preferred communication style, and
escalation history must persist across months of
interactions. Episodic memory records each
interaction: what the customer asked, what was
resolved, what was escalated. The critical
difference from coding agents: retention must be
much longer (1 year minimum), and the forgetting
engine must be conservative — deleting a
customer's history creates a worse experience than
keeping stale data.
C. Research Agents
Research agents need permanent semantic memory.
Sources, findings, hypotheses, contradictions, and
connections between papers form a growing
knowledge graph that becomes more valuable over
time. Episodic memory records which papers were
read, what was extracted, and which search queries
produced useful results. Procedural memory
captures research methods: how to search, how to
evaluate, how to synthesize. The forgetting engine
should never expire semantic facts in a research
context — supersede outdated findings instead.
 XV. TESTING YOUR MEMORY SYSTEM
 How to verify that memory actually works
A. The Amnesia Test
Tell the agent a fact in session 1. Close the session.
Open session 2 and ask the agent to recall the fact.
If it cannot, episodic or semantic memory is not
working. This is the minimum viable test for any
memory system.
B. The Contradiction Test
Store two conflicting facts: "user prefers Python"
and "user prefers TypeScript." Ask the agent which
language the user prefers. If it confidently answers

Anthropic
12
one without acknowledging the conflict, the
contradiction detection is not working. The correct
behavior: flag the conflict and ask the user to
resolve it.
C. The Staleness Test
Store a fact with a 30-day TTL. Wait (or simulate)
31 days. Ask the agent about the fact. If it still uses
the expired fact, the forgetting engine is not
running. The correct behavior: the fact should be
expired and the agent should indicate it does not
have current information.
D. The Skill Promotion Test
Complete the same task type successfully three
times. On the fourth attempt, verify that the agent
uses the saved skill instead of re-planning from
scratch. If it re-plans, procedural memory is not
triggering. The correct behavior: the agent loads the
skill and follows its steps, only deviating if the
preconditions are not met.
E. The Load Test
Fill episodic memory with 10,000 entries. Measure
retrieval latency. If retrieval takes more than
500ms, the store needs indexing or the retrieval
algorithm needs optimization. For semantic
memory, insert 5,000 facts and verify that conflict
detection still runs in under 1 second. Memory
systems that work at 100 entries and fail at 10,000
are not production-ready.
Memory System Test Checklist
- Agent recalls fact from previous session (amnesia test)
- Agent detects conflicting facts (contradiction test)
- Expired facts are not used (staleness test)
- Repeated success triggers skill (promotion test)
- Retrieval under 500ms at 10K entries (load test)
- Forgetting engine runs on schedule (cron test)
- Multi-session task preserves progress (continuity test)
- Cross-project facts do not leak (isolation test)
 XII. CONCLUSION
The model got 10x smarter. It still forgets
everything after every session. Memory — not
intelligence — is the bottleneck in 2026. The
five-layer architecture solves this: working memory
for the current turn, episodic memory for what
happened, semantic memory for what is true,
procedural memory for how to do things, and a
forgetting engine for what to delete.
 The evidence is concrete: Mem0 cut token usage
by 90% and latency by 91% by storing 1,800 tokens
per query instead of 26,000. Snowflake added one
ontology layer and gained 20% accuracy with 39%
fewer tool calls. Memory pays for itself on day one.
 The practical recommendation: start with
episodic memory. One JSON file that saves task
outcomes and queries them before starting new
work. This costs minutes to build and immediately
prevents the agent from repeating yesterday's
mistakes. Then add semantic memory for durable
facts. Then procedural skills for methods that work.
Then a forgetting engine to keep everything clean.
The architecture compounds: each layer makes the
others more valuable.
"Tomorrow it reads the same twelve files, reaches the same
conclusions, and charges you the same tokens. Unless you give it
memory."
